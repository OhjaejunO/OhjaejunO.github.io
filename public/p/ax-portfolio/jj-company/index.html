jj-company — 무엇을 맡길지 «등급»으로 정한다

매일 도는 에이전트 3종 · 결정적 감사 1건 · 시범 감시 봇 1건. 판단이 아니라 규칙이 권한을 가릅니다.

0회사 구조 — 경계 4 · 뷰 3

원페이지의 그 한 장과 같은 파일입니다. 경계는 넷 — 작업장(main 고정 · 커밋 금지 · worktree → PR), 운영 서버(git pull 로만 갱신 · 스케줄 CWD), 에이전트(A/B 등급 · default 모드 · 매 회차 프로브), 출장지·외부(읽기 전용 · 예외는 지정 목록·단방향). 뷰 셋은 정관의 세 질문입니다 — 아침 회차(무엇이 언제 돌고 어디에 남는가), 발행 장치(무엇이 승인이고 누가 올리는가), 경계와 정본(어디까지가 쓰기이고 무엇이 정본인가). 컴포넌트 22 · 간선 21 · 경계 4 · 카드 3이고, 도식은 archify 검증(showcase 9항 · 오류 0)을 통과한 JSON 에서 생성됩니다 — 그림을 손으로 그리지 않고, 검사를 못 넘으면 갱신되지 않습니다.

1왜 등급인가

에이전트에게 일을 맡길 때 가장 위험한 건 «이 정도는 알아서 하겠지»입니다. 그 판단이 사람마다, 세션마다 다르면 언젠가 되돌릴 수 없는 일이 자동으로 실행됩니다. 그래서 맡길 범위를 판단이 아니라 등급으로 고정했습니다.

A
완전 자동
read-only 감사·리포트 생성. 파일 수정 없음. 사람 승인 불필요.
B
제안까지 자동
콘텐츠 초안·카드 제안·커밋 준비. 산출물은 reports/로만. 발행·승격은 사람.
C
사람 필수
발행·배포·외부 발송·결제. 되돌리기 어려운 git 동작도 여기 — force push, 브랜치 삭제, 원격 이력 변경.
가르는 기준은 «파일 종류»가 아니라 «되돌림 비용»입니다. revert 한 번으로 안 돌아오는 순간 등급이 올라갑니다. 이 한 문장이 경계 판정을 사람 취향에서 규칙으로 옮깁니다.

자율성 사다리 — 등급을 가로지르는 축

등급은 «무엇을»이고, 사다리는 «어디까지»입니다. 워커 하나가 어느 단까지 올라가는지를 명세(양식)에 적습니다.

1
Research
조회·수집. 읽기 전용. 감시 봇·스카우트 보조
2
Draft
초안·후보 생성. 산출물은 reports/·logs/. 훅 브레인스토머·유통 변환 초안
3
Recommend
판정 후보·지적 목록. 크로스 모델 검수는 여기서 멈춘다 — 판정은 내지 않는다
4
Approve
결정적 게이트가 통과/실패를 내린다. LLM 은 자문, 게이트가 정본
5
Execute
스키마·게이트를 경유한 쓰기만. 정본 직접 쓰기 금지
발행·외부 접촉·과금·비가역 동작은 등급과 무관하게 JJ 게이트입니다. 사다리 5단에 올라간 워커도 이 넷은 못 넘습니다 — 정관 C등급 조항과 «되돌리기 어려운 git 동작도 C등급» 이 그 자리입니다.

3조용한 실패를 막는 장치

자동화에서 가장 위험한 건 실패가 아니라 «실패했는데 아무 일도 없어 보이는 것»입니다. 로그가 조용하면 «동작했다»로 읽히고, 그 위에 다음 작업이 얹힙니다.

  • 감지 장치가 실제로 값을 담는지 검증한다. 형식만 맞고 값이 비면 장치가 없는 것보다 위험합니다 — 「기록되고 있다」로 보이기 때문입니다.
  • 검사에는 역검증을 같이 둔다. 일부러 걸려야 하는 입력을 넣어 검사가 헛돌지 않는지 확인합니다.
  • 역검증 케이스는 다른 검사가 같이 걸리지 않게 분리한다. 분리하지 않으면 «그 검사가 없었어도 잡혔을 입력»인지 알 수 없습니다.
  • 검사는 쓰기 전에 한다. 파일을 먼저 만들고 색인에서 실패하면 반쪽 상태가 남아, 다음 사람이 무엇이 끝났는지 알 수 없습니다.

실제로 이 조항들이 나온 사고

  • 로그에 판본을 남기게 했으나 셸 인자 우선순위 탓에 빈 값이 찍혔습니다. 대응책 자체가 조용한 실패를 일으킨 경우입니다.
  • 저장은 되는데 조회가 영원히 안 되는 경로가 있었습니다. 파일명이 색인 정규식 밖이라 다음 회차가 같은 산출물을 다시 만들었고 비용이 조용히 샜습니다.
  • 네 작업이 같은 초에 동시 기동해 git pull이 경쟁, 둘이 죽었습니다. 시작 지연을 상수로 분산하고 pull에 재시도를 넣어 12/12로 복구했습니다.

감지 층 — 무엇이 «조용히» 실패하는지를 기계가 본다

장치무엇을 잡나실물
무기록 종료 감지래퍼가 시작 시 .started 스탬프를 쓰고 정상 종료 시 지운다. «start 는 있는데 STATUS 가 없는» 회차와 잔존 스탬프를 감사 데이터로 판독logs/<작업>.started · scripts/run_audit.py → ops-auditor 점검 항목 9. 계기: 재부팅으로 stagger 수면 중 죽은 회차 2건이 로그 어디에도 없었다

5크로스 모델 자문 층 — 결정적 게이트가 정본, LLM 은 자문

게이트가 통과시킨 발행 예정 텍스트를 다른 모델이 체크리스트로 다시 봅니다. 간선의 방향이 핵심입니다 — 게이트 → 자문이지 그 반대가 아닙니다. 자문이 🔴 를 내도 게이트 판정은 바뀌지 않고 리포트에 병기됩니다.

항목실물
실행체헤르메스 프로필 gumsu · 모델 pin nemotron-3.5-lightning-free(무료 프로바이더) · 메모리 off · 도구 없음
입력공개 예정 텍스트만(카드·캡션·고정 댓글·킷 본문) + 조문 번호 참조형 체크리스트 C1~C12 + 조문 절 발췌. 정관·검증로그·FACTS 는 넣지 않는다
정지 조건모델명이 pin 과 다르거나 프로바이더가 실패하면 «검수 미수행»으로 기록 — 조용한 전환 금지
1일차 실측ep31 지적 6건 → 채택 3 / 기각 3 (keep rate 50%). 오탐 1건의 원인은 체크리스트가 정본보다 좁게 적힌 것 — 체크리스트를 «규칙 재서술» 에서 «조문 참조 + 발췌» 로 바꾸자 재실행에서 채택 3건만 정확히 재현
왜 두나게이트가 못 보는 축이 있다 — 수치는 같은데 비교의 방향이 뒤집힌 문장(A>B ↔ B>A). 결정적 수치 대조(guard 3)의 사각이고, 첫 실증은 시범 봇이 잡았다

6Learning 폐루프 — 교정이 정관으로 돌아오는 길

세션에서 생긴 교정은 종류별로 자리가 다릅니다. 자리를 잘못 잡으면 메모리에만 쌓여 다음 세션이 못 보거나(재고 25건), 정관에 기법이 들어갑니다.

교정정본 자리
R1 낡은 사실편 FACTS · 스키마 레코드 · 실값 (옛 값은 PREV 로 남겨 게이트가 잔존을 잡는다)
R2 결정기록(검증로그 §N · PR 본문) — 정관엔 안 쓴다
R3 반복 선호·작업 규칙정관 — 조항 + 근거 실측 1줄, 가능하면 장치
R4 기법·채널 규격제작 규약(SKILL) — 판본 번호·적용 시작 편
R5 시퀀스워커 정의·스크립트 독스트링
R6 위험 동작게이트·가드 코드 — 검사 + 역검증 양쪽, 조문은 구현 참조
R7 교훈learnings — 한 줄 + 근거 + 날짜, 승격되면 «→ 정관 §N» 표기

판별 순서는 R1 → R6 → R4/R5 → R3 → R7 → R2 — 사실이면 값부터, 위험이면 장치부터, 문서는 그다음입니다. 등재 전 기존 조문 대조가 필수입니다: 재고 33건 중 4건이 이미 등재돼 있었고, 그중 하나는 «조항이 있는데 못 읽어서» 사고까지 냈습니다. 헤르메스 봇은 7자리가 승인됐고 2자리가 가동·사흘 시범 중입니다.

4아침 리포트 실물

아래는 ops-auditor가 실제로 남긴 리포트입니다. 개인 경로·계정·메일은 마스킹했습니다(<vault>, <repo>, <user>). 판정에 쓰인 수치와 «데이터값 vs 실측치»가 갈리는 지점을 그대로 두었습니다.
