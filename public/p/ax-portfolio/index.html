아래 한 장이 회사 전체입니다. 대표실(JJ)에서 지시가 작업장으로 가고, 작업장은 worktree 와 PR 로만 main 에 닿고, 운영 서버는 그것을 pull 로만 받습니다. 운영 서버 안에서 스케줄러가 래퍼를 띄우고, 래퍼가 동기화·권한 프로브를 지나 에이전트 다섯(운영·마케팅·영업·감리·헤르메스)을 부르며, 결과는 STATUS 줄이 붙은 리포트로 쌓입니다. 발행은 채팅이 아니라 승인 파일이 서명이고, 인스타그램은 사람이 올리는 C등급으로 따로 그렸습니다. 경계 4개(작업장 · 운영 서버 · 에이전트 · 출장지)와 카드 3장(자동화 3등급 · 정본은 실물 · 경계 규칙)이 정관 §0~§6 을 그대로 옮긴 것입니다.

같은 회사를 사무실 한 장으로도 봅니다. 위 도식의 에이전트 아홉이 각자 책상에 앉아 있고, 상태는 말이 아니라 실물에서 읽습니다 — 클로드·코덱스·그록의 세션 기록 파일, 헤르메스의 상태 DB, 스케줄 로그의 STATUS 줄, 오늘 생긴 리포트 파일. 리포트가 생기면 그 캐릭터가 일어나 대표 자리까지 걸어가 건네고, 상단 수치 띠(발행 편·게시물·게이트 절·열린 PR·스킬 판본)와 오른쪽 승인 대기 큐는 발행로그·GitHub·리포트 폴더를 읽어 30초마다 갱신됩니다. 캐릭터를 누르면 그 에이전트가 일하는 터미널로 넘어갑니다.

이 구조를 부르는 말

각 항목의 수치는 전부 실물에서 센 값입니다.

graph of loops — 파이프라인은 직선이 아니라 되돌아가는 루프의 그래프다. 축 전환 한 번이면 5~12단계를 다시 탄다.
hard verify gate — 결정적 검사 24항. 통과 못 하면 사람이 설득해도 나가지 않는다.
node contract — 노드 사이 인계는 스키마가 정본(필수 7 · 층위별 URL 하한 · 재시도 상한 3). 정의 문서는 스키마를 참조한다.
stop condition — «프로바이더 실패·모델 변경 시 조용한 전환 금지, 중단·보고». 봇마다 FAIL CONDITION 으로 명문화.
anchor — 실물을 조회할 수 있는 것은 실물이 정본이고 문서는 조회 결과. 스케줄 트리거·필드 목록·배포 상태.
fake-edge test — 화살표마다 «앞 산출물을 실제로 읽는가». 12개 중 6개가 가짜였다.
cost per accepted change — 크로스 모델 자문의 keep rate: 3/6 = 50%. 50% 미만이면 그 자리를 접는다.
decision latency — 편 스팬의 97~98% 는 기계가 아니라 사람 판단과 재작업. 절감은 앞단 pre-flight 에서 난다.
correction routing — 교정은 R1 낡은 사실 → R6 위험 동작 → R4/R5 기법·시퀀스 → R3 정관 → R7 교훈 → R2 결정 순으로 자리를 찾는다. 등재 전 기존 조문 대조 필수(재고 33건 중 4건이 기등재였다).

이 페이지는 검색에 노출되지 않는 비공개 경로입니다(robots.txt 제외 대상). 지면에 적은 수치는 전부 실물에서 센 값이고, 확인하지 못한 것은 적지 않았습니다. 최신값은 본문과 각 문서 페이지에 있습니다.
