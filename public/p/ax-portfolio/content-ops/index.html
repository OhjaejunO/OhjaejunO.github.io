content-ops — 상태를 사람이 들고 있다가 사고가 났다

기능을 늘리는 대신 하나만 합니다. 에피소드의 상태와 그 근거를 기록하고, 판단은 기록을 보고 하게 만드는 것.

1문제 — 사고 세 건, 원인은 하나

혼자 기획하고 만들고 올리다 보면 각 편이 지금 어느 단계인지를 결국 머릿속에서 관리하게 됩니다. 소재를 모아둔 곳, 대본을 쓴 곳, 실제로 올린 곳이 흩어져 있으니 «이건 올렸던가?»를 판단할 근거가 기억밖에 없습니다.

  • 오판 — 제작만 해두고 발행하지 않은 건을 발행했다고 착각해 그대로 묻어버림
  • 중복 노출 — 이미 다룬 소재를 다시 다뤄 같은 내용을 두 번 내보냄
  • 취소 이력 증발 — 왜 접었는지가 남지 않아 나중에 같은 판단을 반복

셋 다 원인이 같습니다. 상태를 사람이 들고 있었다는 것.

2설계 판단 두 개

① 제작완료와 발행완료를 절대 같은 칸에 두지 않는다

오판 사고가 정확히 이 둘을 뭉뚱그린 데서 나왔습니다. 만들어 둔 것과 내보낸 것은 다른 상태입니다. cancel_reason도 같은 이유로 존재합니다 — 접었다는 사실만으로는 다음 판단에 도움이 되지 않고, 왜 접었는지가 남아야 같은 소재를 다시 집어들 때 근거가 됩니다.

필드설명
number에피소드 번호 (고유)
title제목
categoryAI소식 / 두드려봄 / 기회 / 꿀팁
status제작중 / 제작완료 / 발행완료 / 발행취소
published_at발행일 (미발행 시 비어 있음)
cancel_reason취소사유 (취소 건이 아니면 비어 있음)

② 노출 횟수를 세는 단위는 «소재»가 아니라 «사건»이다

서로 다른 URL 여러 개가 같은 사건을 다루는 것이 실제 중복 노출 사고의 형태였습니다. URL 단위로 세면 정작 문제가 된 경우가 그대로 통과합니다.

exposure_count는 연결된 에피소드 중 발행완료만 셉니다. 제작만 해둔 건과 접은 건은 밖으로 나가지 않았으므로 노출이 아닙니다 — 중복 노출의 기준은 «만들었는가»가 아니라 «내보냈는가»입니다.

접힌 에피소드도 사건에 연결된 채로 남습니다. 그래야 «이건 왜 접었나»를 취소사유 텍스트가 아니라 조회로 답할 수 있습니다.

3중복 감지 — 모델은 후보까지, 채택은 사람

새 소재가 이미 다룬 것과 겹치는지를 임베딩으로 걸러냅니다. 모델은 BAAI/bge-m3이고 로컬에서 돕니다 — 아직 발행하지 않은 기획이 외부 API로 나가지 않게 하려는 것입니다.

모델이 하는 일은 후보를 좁히는 것까지입니다. 겹친다/아니다의 최종 판정은 사람이 합니다. 판정을 모델에 맡기면 «왜 이게 중복인가»를 설명할 수 없고, 설명할 수 없는 판정은 다음에 같은 상황이 왔을 때 근거가 되지 못합니다.

이것은 다른 프로젝트와 같은 원칙입니다 — 판정은 결정적 규칙, LLM은 보조. 토망치랩의 발행 게이트, jj-company의 자동화 등급, AX 시딩 엔진의 쿠폰 프로토콜이 전부 같은 판단 위에 있습니다.
