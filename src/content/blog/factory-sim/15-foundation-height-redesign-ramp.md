## 1. 들어가며 — 만든 걸 갈아엎다

[14편](/blog/factory-sim/14-foundation-basics)에서 Foundation을 경사지에 계단처럼 안착시키는 높이 스냅을 만들었습니다. 상면 = `평면 + Thickness + N×100`, 풋프린트 최고 지형점 위로 N단 올려서 묻힘 0. 글 끝에서 *솔직히 예고*했죠 — "이 방식은 곧 다시 도마에 오른다"고.

도마에 올린 건 PIE였습니다. 경사지에서 Foundation을 여러 장 깔아보니, 만들 땐 안 보이던 게 드러났어요. 세 가지가 한꺼번에 무너졌습니다.

- **평면이 안 자란다.** 옆에 나란히 깔아도 인접 판이 *각자 발밑 지형*을 따라 제각각 단이 됩니다(N, N+1, N+2…). 넓고 평평한 바닥 — Foundation의 존재 이유 — 을 만들 수가 없어요.
- **컨베이어가 끊긴다.** 단이 갈라진 인접 판에 컨베이어를 걸치면, [14편 5절](/blog/factory-sim/14-foundation-basics)에서 *공짜로 얻었다*고 좋아했던 그 "이높이 면 거부" 규칙이 — 이번엔 *엉뚱한 데서* 발동해 연결을 막습니다.
- **램프가 뜬다.** (이땐 램프를 막 붙이던 참이었어요.) 램프가 이웃 판이 아니라 *지형* 기준으로 떠서, 정작 연결해야 할 판과 높이가 안 맞아요.

만든 지 몇 시간 된 시스템을 갈아엎어야 했습니다. 이번 편은 그 *재설계* — 무엇이 틀렸고, 무엇으로 바꿨고, 14편이 만든 게 어떻게 *살아남았는지*의 이야기입니다.

## 2. 무엇이 틀렸나 — 진실원이 잘못됐다

세 증상을 들여다보면 뿌리가 하나예요. **"Foundation의 높이를 무엇이 정하는가"** 가 틀렸습니다.

14편의 답은 *지형*이었어요. 각 Foundation이 자기 발밑 지형의 최고점을 보고 독립적으로 N단을 정한다. 묻힘을 없애는 덴 완벽했지만, *옆 판을 안 봤다*는 게 함정이었습니다. 지형이 조금만 기울어도 옆 판은 다른 단이 되고, 그렇게 단이 갈라지면 평면도 컨베이어도 램프도 줄줄이 무너지는 거죠.

여기서 *참조 게임*을 봤습니다 — 새티스팩토리. 같은 장르의 Foundation은 어떻게 동작할까? 정반대였어요. **새티스팩토리는 지형을 무시합니다.** Foundation을 깔면 *인접 Foundation의 높이를 이어받아* 평면이 옆으로 자라고, 지형이 그 평면을 파고들면 그냥 *지형이 슬래브에 박히게* 둡니다. 램프도 지형이 아니라 *이웃 판 엣지*에 스냅하고요.

즉 진실원이 **지형이 아니라 이웃 판**이어야 했습니다. 지형은 *맨 첫 판*을 놓을 때나 기준이 되는 거고요. 문제는 산식(`N=ceil(...)`)이 아니라, 그 산식을 *언제 누구에게* 적용하느냐였던 거죠. 그래서 고치는 건 산식이 아니라 **높이 결정의 우선순위**입니다.

```
① 인접 Foundation 있음  → 높이 상속 (이웃 SurfaceZ 그대로 — 평면 확장, 기본 경로)
② 고립(인접 없음) 첫 장 → 14편 N 산식 (풋프린트 max GroundZ 스냅 — "씨앗")
③ 램프               → 인접 판 엣지 스냅 (낮은 끝 = 이웃, 높은 끝 = +1단)
```

## 3. 새 정책 — 이웃을 상속한다

새 우선순위가 들어가는 자리는 한 곳, `OJJ_ComputeSnapLift`입니다. [14편 6절](/blog/factory-sim/14-foundation-basics)에서 "다음을 위한 포석"으로 미리 분리해 둔 그 가상 훅 — 바로 여기에 재설계가 떨어집니다.

```cpp
float AOJJ_Foundation::OJJ_ComputeSnapLift(const AOJJ_Grid& Grid, FIntPoint Origin, FIntPoint EffSize,
    int32 RotationSteps, FString* OutHeightSource) const
{
    // F3.5 ①: 이웃 상속 — 평면 확장이 기본(지형 클리핑 허용). 상속값은 이웃 SurfaceZ =
    // 평면+Thickness+N×100 이라 자동으로 단 격자 위 — 리프트(평면 기준)로 환산만 하면 됨.
    // stale 이웃은 그리드 조회가 weak 검증으로 거름(유령 단 차단).
    const float SnapGridOriginZ = Grid.GetActorLocation().Z + Thickness;
    float NeighborZ = 0.0f;
    int32 ContactCells = 0;
    if (Grid.OJJ_GetNeighborFoundationSurfaceZ(Origin, EffSize, SnapGridOriginZ, NeighborZ, ContactCells))
    {
        if (OutHeightSource) { *OutHeightSource = FString::Printf(TEXT("상속(이웃 접촉 %d셀)"), ContactCells); }
        return NeighborZ - Thickness - Grid.GetActorLocation().Z;
    }

    // ② 고립 첫 장 = 씨앗: 지형 스냅(14편 산식 — 풋프린트 전체 max GroundZ).
    if (OutHeightSource) { *OutHeightSource = TEXT("씨앗(지형)"); }
    return Grid.OJJ_ComputeFoundationSnapLift(Origin, EffSize, Thickness);
}
```

먼저 둘레의 인접 Foundation을 그리드에 묻습니다(`OJJ_GetNeighborFoundationSurfaceZ` — 풋프린트 4변 둘레 셀을 훑어 면접촉한 이웃 판의 SurfaceZ를 모아 선출). 이웃이 있으면 그 높이를 **그대로 상속**하고 끝이에요. 없으면 그제야 — 함수 맨 아래 — **14편의 `OJJ_ComputeFoundationSnapLift`** 를 부릅니다.

> **14편은 폐기되지 않았다.** 이게 이 재설계에서 제일 마음에 드는 부분이에요. "지형 스냅"이라는 *정책*은 폐기됐지만, 그걸 계산하던 14편 함수는 *한 줄도 안 지웠습니다.* 다만 *역할*이 바뀌었죠 — "모든 Foundation의 높이"에서 "이웃 없는 첫 판, 즉 씨앗의 높이"로 강등됐을 뿐. 폐기된 건 코드가 아니라 *그 함수를 1순위로 쓰던 결정*입니다. 경사지를 처음 개척할 땐 여전히 14편 산식이 첫 판을 지형에 앉히고, 그 옆부터는 상속이 평면을 키워가요.

그리고 상속엔 *공짜 정합*이 따라옵니다. 이웃의 SurfaceZ는 어차피 `평면+Thickness+N×100`이라 **이미 단 격자 위**예요. 그걸 그대로 물려받으니 상속값도 자동으로 격자에 맞고, [14편 5절](/blog/factory-sim/14-foundation-basics)의 `OJJ_GetUniformSurfaceZ` 균일 규칙·걸침 허용·불변식이 *전부 그대로* 성립합니다. 평면이 같은 단으로 경사지를 가로질러 자라고, 그 위 컨베이어는 균일 SurfaceZ라 자동으로 이어져요 — 2절 세 문제가 한꺼번에 풀립니다.

> **유령 단 차단.** 한 가지 함정이 있어요. 이웃 조회가 *파괴된* Foundation의 잔존 셀에서 높이를 주워오면, 실재하지 않는 판에서 단을 상속받는 *유령 단*이 생깁니다. 그래서 둘레 조회는 `GetFoundationSurfaceZ`(weak 포인터 `IsValid` 검증) 경유로만 이웃을 인정해요 — [12편](/blog/factory-sim/12-resource-mining-claim)에서 광맥 선점에 쓴 그 weak 검증과 같은 결입니다. 죽은 판은 상속 후보에서 자동으로 빠져요.

## 4. 지형을 파고들게 둔다 — 클리핑이라는 결정

이웃 상속엔 *대가*가 있습니다. 상속한 평면이 오르막을 만나면 — 평면은 평평한데 지형은 솟으니 — **슬래브가 지형에 박혀요.** 14편이 그토록 없애려던 그 "묻힘"이, 이번엔 *일부러* 생깁니다.

이걸 버그로 볼 수도 있었지만, 받아들이기로 했어요. 새티스팩토리가 정확히 그렇게 동작하거든요 — 평면을 우선하고, 지형이 박히면 박히게 둡니다. 점검해보니 부작용도 견딜 만했고요. 캐릭터는 슬래브 *노출면*부터 걸으면 되고(박힌 부분은 어차피 지형 속), 커서 트레이스나 베이크는 영향이 없었어요.

> **솔직히 수용한 것.** 다만 *묻힌 셀 위에 머신을 놓으면* 그 머신은 지형 아래로 묻힙니다(상속 SurfaceZ가 지형보다 낮으니). 이것도 새티스팩토리와 같은 클리핑이라 *수용*했어요 — "묻힌 셀 배치 거부" 같은 규칙을 새로 달 수도 있었지만, 그건 시각=데이터 단일 진실원을 깨는 예외라 안 달았습니다. 평면 확장이라는 *기본*을 위해 가장자리의 묻힘을 감수하는 거죠. 완벽한 해가 아니라 *일관된* 해를 택한 자리예요.

## 5. 단과 단을 잇다 — 계단으로 분해한 램프

평면은 상속으로 자라지만, *서로 다른 단* 사이는 여전히 끊겨 있어요. [14편 5절](/blog/factory-sim/14-foundation-basics)에서 단차 걸침을 *거부*만 했지 *연결*은 못 했잖아요. 그 연결 수단이 **램프**입니다.

문제는 한 단이 100uu라는 것. 캐릭터 `MaxStepHeight`가 45니까([14편 3절](/blog/factory-sim/14-foundation-basics)) 100짜리 턱은 *걸어서 못 올라가요.* 그래서 램프는 그 100uu를 **여러 행의 계단으로 잘게 분해**합니다. R행짜리 램프라면 행마다 `100/(R−1)`uu씩 올라가게. 이게 셀별 높이를 만드는 `OJJ_BuildPerCellSurfaceZ`예요 — [14편 6절](/blog/factory-sim/14-foundation-basics)의 "셀별 SurfaceZ 배열" 포석이 여기서 쓰입니다.

```cpp
OutCellZs.SetNumUninitialized(EffSize.X * EffSize.Y);
for (int32 LX = 0; LX < EffSize.X; ++LX)
{
    for (int32 LY = 0; LY < EffSize.Y; ++LY)
    {
        // 풋프린트 로컬 → 오르는 방향 행 r (회전 step별 축 매핑, 일부 생략)
        int32 r = 0;
        switch (Step)
        {
        case 0: r = LX; break;                       // 월드 +X
        case 1: r = LY; break;                       // 월드 +Y
        case 2: r = (EffSize.X - 1) - LX; break;     // 월드 −X
        case 3: r = (EffSize.Y - 1) - LY; break;     // 월드 −Y
        }
        // 양 끝 정합(턱 0): r=0 → BaseSurfaceZ 정확, r=R−1 → +RiseSteps×100 정확.
        OutCellZs[LX * EffSize.Y + LY] =
            BaseSurfaceZ + ((float)r / (float)(R - 1)) * RiseSteps * AOJJ_Grid::OJJ_FoundationSnapStep;
    }
}
```

산식은 한 줄이에요 — `SurfaceZ(r) = Z_low + (r/(R−1)) × RiseSteps × 100`. 낮은 끝 행(`r=0`)은 정확히 `Z_low`, 높은 끝 행(`r=R−1`)은 정확히 `Z_low + RiseSteps×100`. **양 끝이 인접 판과 턱 0으로 딱 맞는다**는 게 핵심입니다. `(R−1)/(R−1)=1`이라 float 오차도 없고요. 계단 박스 메시도 *같은 산식*으로 그려서 시각과 데이터가 한 진실원을 공유합니다.

> **Codex가 잡은 버그 — 낮은 끝 기준.** 처음엔 램프의 `Z_low`(낮은 끝 높이)를 *풋프린트 전체의 최고점*으로 잡았어요. 평판에선 맞는 방식이었죠. 그런데 램프는 *경사지가 주 사용처*라, 풋프린트 max로 잡으면 낮은 끝이 *높은 단으로 떠올라* 턱 0이 깨집니다(낮은 끝이 이웃 판보다 높아져요). 그래서 `Z_low` 스냅 기준을 **낮은 끝(r=0) 행의 지형만** 보도록 분리했습니다. 양 끝 정합이라는 램프의 존재 이유가 걸린 한 끗이었어요.

## 6. 알아서 맞추는 램프 — 두 판 사이의 틈을 읽다

램프를 손으로 놓는 것도 되지만, 자동화 게임답게 한 발 더 갔습니다. **램프 모드에서 두 Foundation 사이에 커서를 두면, 그 틈에 맞는 램프가 자동으로 산출돼요.**

원리는 *양방향 이웃 스캔*입니다. 커서의 회전축 양쪽으로 인접 Foundation 라인을 훑어(최대 32칸) 양쪽에서 판을 찾으면 — 그 틈 전체를 풋프린트로 삼고(길이 D칸), 두 판의 단 차이로 `ΔZ`(=k단)를 잡고, **오르는 방향(부호)을 낮은 판→높은 판으로 자동 결정**합니다. 손으로 R키를 돌려 방향을 맞출 필요가 없어요. 이웃의 SurfaceZ는 단 격자 위라 `k`도 *정확한 정수*로 떨어지고요.

그리고 *틈의 크기*에 따라 물류 수단이 갈립니다. 이걸 공식으로 못박았어요.

```
gap 0  → 벨트 직결    (Δ1단이면 컨베이어가 바로 건너감 — 램프 불필요)
gap 1  → 1칸 쐐기      (걷기 불가, 컨베이어 전용 — 좁은 단차)
gap 2+ → 자동 맞춤 램프 (행당 계단 ≤ 45uu 검증 — 걸어 오를 수 있게)
```

자동 맞춤은 행간 계단이 `45uu`(도보 한계)를 넘으면 프리뷰를 빨갛게 막아요 — 틈이 너무 좁아 한 행당 너무 가파르면 "더 긴 틈이 필요하다"고 거부하는 거죠. 한쪽에만 이웃이 있거나 아예 없으면 5절의 고정 램프로 폴백하고, `ΔZ=0`(같은 단)이면 램프 없이 평지 다리로 퇴화합니다.

> **호버 = 배치, 한 길.** 이 자동 산출이 *미리보기*와 *실제 배치*에서 다른 결과를 내면 재앙이에요(보이는 램프와 놓이는 램프가 다름). 그래서 풋프린트 결정을 단일 훅(`OJJ_ComputeHoverFootprint`)으로 모아, 호버와 배치가 *같은 함수*를 부르게 했습니다. [4편](/blog/factory-sim/04-mouse-input-build-controller)·[7편](/blog/factory-sim/07-port-cell-unification) 이래 줄곧 지켜온 "미리보기 = 클릭 판정 단일 진실원"이 여기서도 규칙입니다.

## 7. 마치며 — 평면이 자란다

이번 편 요약은 셋입니다.

1. **진실원을 지형에서 이웃으로 옮겼다.** 14편의 "각 판이 지형에 독립 스냅"은 경사지에서 평면 확장·컨베이어·램프를 다 무너뜨렸다. 새티스팩토리처럼 *이웃 Foundation 높이를 상속*해 평면을 키우고, 14편 산식은 폐기가 아니라 *고립 첫 판의 씨앗*으로 강등했다.
2. **평면을 위해 클리핑을 수용했다.** 상속 평면이 오르막을 파고들어 지형에 박히는 걸 — 새티스팩토리처럼 — 일부러 허용했다. 완벽한 해 대신 *일관된* 해.
3. **단과 단을 램프로 이었다.** 100uu 턱을 행당 `100/(R−1)`uu 계단으로 분해해(`Z_low+(r/(R−1))×RiseSteps×100`) 양 끝 턱 0으로 맞추고, 두 판 사이 틈을 읽어 길이·단수·방향을 자동 산출했다. 낮은 끝 기준을 잘못 잡으면 턱이 깨지던 버그가 한 끗이었다.

14편이 *평평한 땅을 한 장씩* 놓는 거였다면, 이번 편은 그 땅들이 *서로를 보고 한 평면으로 자라게* 만든 일이었습니다. 만든 지 하루 된 정책을 갈아엎는 건 아깝지만, PIE가 보여준 구조적 문제를 산식 땜질로 덮는 것보다 진실원을 바로잡는 게 옳았어요. 이제 경사지에 넓은 공장 바닥이 자라고, 단이 갈리면 램프가 알아서 잇습니다.

다음 편은 그 램프 *위로 물건을 흘려보내는* 이야기입니다. 램프는 걸어 오를 수 있게 됐지만, 컨베이어가 그 빗변을 *부드럽게* 타고 오르려면 또 한 겹의 문제가 있어요 — 계단진 단과 매끄러운 벨트 사이의 간극. 경사 컨베이어와 Foundation 메시 개편으로, 건축의 세 번째이자 마지막 이야기로 갑니다.
