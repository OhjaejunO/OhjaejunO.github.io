> 🏭 **공장 시뮬레이션 게임 개발기 — Phase 3: 자원이 어디서 태어나는가**
> - 12편: [채굴기·광맥·1자원 1머신 선점](/blog/factory-sim/12-resource-mining-claim)
> - **3.2편: 물 시스템 — 다중 셀 수원·공유 펌프·경사 통과 파이프** ← 현재 글 (12편 Phase 3.1에서 이어지는 자원 생성 편)
> - (이어지는 편: 경사 컨베이어·메시 개편 — 예정)

12편에서 광맥을 다뤘다. 광맥은 단순했다. 한 셀에 하나, 채굴기 하나가 선점(Claim)하면 끝. 1자원 1머신.

물은 전부 반대였다. 강은 길쭉하게 여러 셀에 걸쳐 있고, 한 웅덩이에서 펌프 여러 대가 동시에 길어 올려야 하고, 길어 온 물은 파이프를 타고 절벽 위 탱크까지 올라가야 한다. "자원이 어디서 태어나는가"라는 Phase 3의 같은 질문인데, 광맥의 답을 그대로 쓸 수 있는 게 하나도 없었다.

이 글은 그 차이를 세 덩어리로 푼 기록이다 — **격자가 맵을 못 덮던 문제**, **펌프가 자기를 수원으로 착각하던 버그**, **파이프가 물가 절벽 앞에서 멈추던 증상**.

---

## 1. 격자가 행성 맵을 못 덮고 있었다

물을 배치하려고 강 메시 옆에 펌프를 놓으려는데, 멀리 있는 웅덩이가 배치 유효 범위 밖이라고 거부됐다. 원인은 격자였다.

기존 `GridSize`는 300이었다. 셀 크기를 곱해도 행성 맵 전체를 덮지 못했고, 액터 원점(맵 중심)에서 멀어진 강은 아예 격자 바깥이었다. 격자 밖은 placement validator가 "유효하지 않은 셀"로 보니, 그 위엔 아무것도 못 놓는다.

`GridSize`를 **300 → 1008**로 키웠다. 맵 전체 100,800uu를 커버하는 크기다. 코드 변경이 아니라 `L_Planet.umap` 레벨 데이터의 인스턴스 오버라이드(`EditAnywhere` 프로퍼티)만 바꾼 거라, 로직은 한 줄도 안 건드렸다.

그다음이 진짜 문제였다. 격자는 커졌는데 **물로 분류된 셀이 0개**였다.

격자는 각 셀을 buildable / blocked / water 등으로 분류한다. 분류 기준에 `WaterSurfaceZ`라는 임계선이 있는데, 이 값이 -10000이었다. 수면보다 한참 아래라, 어떤 셀도 "물"로 안 잡혔다. 강은 맵에 멀쩡히 흐르는데 격자는 물을 모르는 상태.

실측으로 기준선을 맞췄다. 웅덩이 바닥(랜드스케이프 최저) -997, WaterArea 수면 평면 -980. 그래서 임계선을 **-980**으로 올렸다. 이 보정 후 water 셀이 0 → **19,370개**로 살아났고, buildable 248,458개는 그대로였다(blocked였던 셀이 water로 이동했을 뿐, 건축 가능 면적은 불변).

> ⚠️ **수치 주의 (PIE 확인 후 보강 예정):** 위 -980은 #197 작업 당시 `L_Planet` 레벨 인스턴스 기준 값이다. 현재 코드의 `WaterSurfaceZ` 기본값과 전역 `IsCellWater` 판정 기준은 이후 별도로 분기됐다(레벨의 물 분류 vs 펌프/파이프 런타임 판정이 다른 경로일 수 있음). "물 셀이 0 → 19,370으로 살아난" 서사 자체는 #197 시점 그대로 정확하지만, "현재도 -980"이라고 단정하진 않는다. PIE에서 두 경로의 실제 값을 확인하면 이 자리를 한 문단으로 보강할 것.

여기서 배운 것 하나 — **격자 기반 게임에서 "유효 범위"는 디자인이 아니라 데이터다.** 강을 아무리 멋지게 깔아도 격자가 그 좌표를 모르면 게임은 강의 존재를 모른다. 비주얼과 시뮬레이션 격자는 별개이고, 둘을 잇는 건 임계값 한 줄이다.

## 2. 광맥과 물은 무엇이 다른가 — 다중 셀, 그리고 선점 없음

물의 본체는 `AWaterArea`다. 광맥과 같은 `AResourceBase`를 상속하지만, 결정적으로 두 가지가 다르다.

### 다중 셀 등록

광맥은 단일 셀에 등록한다. 부모 `AResourceBase`가 셀 하나를 격자에 올리고 끝. 강은 그럴 수 없다. "강은 길쭉하게"라서 기본 3×1 영역(`AreaSizeInCells`)을 차지한다.

`RegisterToGrid`를 override해서 영역 전체를 **원자적으로 일괄 등록**했다. 핵심은 원자성이다 — `AreaSizeInCells` 범위를 `OJJ_RegisterActorCells`로 한 번에 등록하되, **한 셀이라도 충돌하거나 off-grid면 전체가 실패**한다. 강이 절반만 등록되는 어중간한 상태를 원천 차단한 것이다.

그리고 광맥의 단일 셀 등록 경로는 손대지 않았다. WaterArea는 override로 자기 경로를 새로 깔았을 뿐, 12편의 광맥 코드는 그대로다. **리그레션 0** — 새 기능을 추가하면서 기존 동작을 안 건드리는 게 이 프로젝트의 원칙이다.

### 선점(Claim)이 없다

이게 광맥과 물의 철학적 차이다.

광맥은 `form="ore"`, **1자원 1머신 선점**이다. 채굴기 하나가 광맥을 `IsClaimed`로 잠그면 다른 채굴기는 못 붙는다(12편).

물은 `form="liquid"`, **무한 수원**이다. 생성자에서 `bIsInfinite=true`를 강제하고, `Claim`을 아예 안 쓴다. 그래서 펌프 여러 대가 같은 웅덩이를 동시에 공유한다. 강에서 물을 길어 올리는 데 "내가 먼저 찜했으니 넌 못 써"가 있을 이유가 없다.

부수적으로 영역 전체를 덮는 **Pawn 진입 차단 볼륨**도 깔았다. 단, 충돌 채널을 `ECC_Pawn`만 Block하고 나머지는 Ignore로 뒀다 — 빌드 커서 트레이스가 물 볼륨에 걸려서 배치가 막히면 안 되니까. 흐름 머티리얼의 `FlowVelocity`는 MID(머티리얼 인스턴스 다이내믹)로 주입해서 강마다 흐르는 방향을 다르게 줬다.

## 3. 펌프가 자기 자신을 수원으로 착각했다

펌프(`APump`)는 물 위에 직접 설 수 있다. `CanStandOnWater()`가 `true`를 반환하고, 수면 Z에 자동으로 안착한다. 채굴기가 광맥 옆에 붙는 패턴을 미러링하되, `IsClaimed` 판정만 없앤 구조다 — footprint 4방향 인접 셀(또는 발밑)에 `form=="liquid"` 수원이 하나라도 있으면 배치 가능.

여기서 고약한 버그가 나왔다. **펌프를 물 위에 놓으면, 펌프가 자기 자신을 수원으로 반환했다.**

원인은 격자의 `OccupiedCells`가 셀당 단일 슬롯이라는 데 있었다. 펌프가 물 위 셀을 점유하는 순간, 그 슬롯에 들어있던 발밑 WaterArea 참조를 펌프가 덮어썼다. 그래서 펌프가 "내 발밑에 뭐 있나?" 물으면 자기 자신이 나왔다.

해결은 **레이어 분리**였다. 머신 점유(`OccupiedCells`)와 자원 조회를 같은 슬롯에서 다투게 두지 않고, 자원 전용 레이어 `GetLiquidResourceAtCell`을 따로 뒀다. 이 레이어는 머신 점유와 무관하게 발밑 WaterArea를 보존한다. 펌프가 위에 올라타도 물은 물대로 거기 있다.

```cpp
// #182 발밑 우선: footprint가 물 위면 발밑 WaterArea 채택(자원 전용 레이어 조회)
for (const FIntPoint& Cell : Footprint)
    if (AResourceBase* Under = Grid->GetLiquidResourceAtCell(Cell))
        return Under;

// 폴백: footprint 바깥 4방향 인접 — 채굴기와 달리 IsClaimed 판정 없음(무제한 공유)
for (const FIntPoint& Cell : Footprint)
    for (const FIntPoint& Dir : Dirs)
    {
        const FIntPoint Neighbor = Cell + Dir;
        if (AResourceBase* Res = Grid->GetLiquidResourceAtCell(Neighbor))
            return Res;
    }
```

발밑 우선, 인접 폴백. 채굴기 코드와 거의 같은 모양이지만 `IsClaimed`를 묻는 줄이 없다 — 그게 공유 수원과 선점 자원의 코드 레벨 차이다.

이 레이어 분리에는 공짜 보너스가 있었다. 웅덩이마다 수면 Z가 다를 때(WA1과 WA2의 Z가 다름), 펌프가 발밑 WaterArea를 정확히 집어 오니 per-puddle 수면 Z 안착이 자동으로 맞는다.

## 4. 파이프는 물가 절벽 앞에서 멈추면 안 된다 — Policy 1

물을 길었으니 보내야 한다. 파이프(`APipe`) 차례다.

증상부터: **두 물웅덩이가 있는데, 한쪽만 펌프→탱크 연결이 됐다.** 똑같이 깔았는데 한쪽 파이프가 중간에 끊겼다.

디버깅해보니 버그가 아니었다. 물가에 절벽이 있었고, 그 절벽의 높이차가 `|dZ| ≈ 714`였다. 격자에는 경사 게이트(STEP 게이트)가 있어서, 인접 셀 사이 `|ΔZ| > 300uu`면 "절벽"으로 보고 연결을 거부한다. 714는 300을 한참 넘으니 정상적으로 차단된 것이다.

문제는 이 게이트가 **컨베이어를 위한 규칙**이라는 거다. 컨베이어는 중력에 의존한다 — 아이템이 굴러가야 하니 가파른 절벽은 막는 게 맞다. 하지만 파이프는 **압송(pressure-fed)**이다. 펌프가 압력으로 밀어 올리니, 수직 둑이든 절벽이든 넘어서 연결돼야 한다.

그래서 **파이프를 컨베이어 경사 validator에서 완전히 면제**했다(Policy 1). 대신 파이프는 셀별 면 Z를 독립적으로 추종한다. 우선순위는 명확하다 — **물 수면 > Foundation 상면 > 지형 GroundZ > 평면**.

```cpp
// #182 파이프 셀별 안착 Z. 우선순위: 물(수면) > Foundation(상면) > 지형(GroundZ) > 평면
float Z = 0.0f;
if (GetWaterSurfaceZAtCell(Cell, Z)) return Z;                 // 1) 물 수면

// … Foundation 상면 분기 …                                    // 2) Foundation

if (OJJ_HasValidGroundZData() && IsValidGridCell(Cell))        // 3) 지형 추종
    return GetActorLocation().Z + CellGroundZQuant[OJJ_CellLinearIndex(Cell, GridSize)];

return GetActorLocation().Z;                                   // 4) 평면 폴백
```

이 결정은 혼자 내리지 않았다. "경사 제한을 푸는" 변경은 게임 전체의 배치 규칙을 건드리는 거라, Codex 교차검증을 돌렸다. 컨베이어는 중력 의존이니 게이트 유지, 파이프는 압송이니 면제 — 매체의 물리가 다르면 규칙도 갈라야 한다는 데 동의가 나왔다. (이 교차검증 흐름은 5편 Codex Adversarial Review에서 다룬 그 방식이다.)

마지막으로 시각 문제 하나. 파이프가 Foundation 데크에서 지면으로 내려갈 때, 수직 전이를 셀 중심에서 하면 데크를 관통해버린다. 그래서 전이를 셀 중심이 아니라 **데크 엣지 바깥**(`HalfCell + OJJ_PipeEdgeDropMargin`)에서 ㄴ자로 꺾는 엣지 라이저를 넣었다.

## 5. 정리 — 같은 Phase, 다른 답

12편과 16편은 둘 다 Phase 3, "자원이 어디서 태어나는가"다. 하지만 광맥의 답을 물에 그대로 쓸 수 있는 건 하나도 없었다.

| | 광맥 (12편) | 물 (16편) |
|---|---|---|
| 셀 | 단일 셀 | 다중 셀(원자적 등록) |
| 접근 | 1자원 1머신 선점(Claim) | 무한 공유(Claim 없음) |
| form | `"ore"` | `"liquid"` |
| 머신 | 채굴기 | 펌프(물 위 안착) |
| 운반 | 컨베이어(중력, 경사 게이트) | 파이프(압송, 경사 면제) |

핵심을 하나만 꼽으면 — **"같은 베이스 클래스, 다른 정책"**이다. WaterArea는 ResourceBase를 상속하되 등록·선점·운반 정책을 전부 새로 깔았고, 그러면서 광맥 경로는 한 줄도 안 건드렸다. 새 자원을 추가할 때 기존 자원을 깨지 않는 것 — 이게 자원이 늘어나도 시스템이 무너지지 않는 이유다.

다음 편은 경사 컨베이어와 메시 개편으로 돌아간다.
