> 🏭 **공장 시뮬레이션 게임 개발기 — 막간: 빌드 비주얼**
> - 관련: [1.3편 머티리얼 그리드 시각화](/blog/factory-sim/03-material-grid-visualization)
> - **막간: 보이지 않으면 못 짓는다 — 고스트 프리뷰·그리드 시각 위계** ← 현재 글
> - (이어지는 편: 경사 컨베이어·메시 개편 — 예정)

1.3편의 호버를 기억하는지. 커서를 그리드에 올리면 그 밑 바닥칸이 초록(놓을 수 있음)이나 빨강(못 놓음)으로 칠해졌다. ISM 타일로 셀을 색칠하는 방식이었다.

머신이 늘면서 그게 부족해졌다. 바닥칸 색은 **풋프린트 면적**은 보여주지만, 실제 지을 물건이 **어떤 모양**으로 **어느 방향을 보고** 놓이는지는 못 보여준다. 컨베이어처럼 입출구가 있는 방향성 머신, 펌프처럼 키 큰 메시 — 이런 건 "여기 2×2칸이 비었다"가 아니라 "이 머신이 이렇게 놓인다"를 봐야 한다.

그래서 호버를 **반투명 고스트 메시**로 진화시켰다(#187). 그런데 그 과정이 함정 투성이였다 — Nanite 때문에 고스트가 아예 안 보이고, 반투명끼리 색이 섞여 빨강이 주황이 됐다. 이 글은 빌드 비주얼을 처음부터 다시 본 막간이다. Phase 1의 머신부터 Phase 4의 사다리까지, 그동안 만든 모든 걸 한 번에 비추는 시스템 이야기.

---

## 1. 바닥칸 색칠로는 부족했다 — 고스트 메시 (#187)

핵심 결정부터: **호버 때 실제 메시를 반투명으로 띄운다.** 단, 머신을 진짜로 스폰하지는 않는다.

매 호버마다 머신 액터를 진짜 스폰하면 낭비가 크고 부작용도 난다(생성자 로직, 콜리전, 등록 훅 등이 다 돈다). 그래서 **단일 `GhostMeshComp` 하나**만 두고, 머신 CDO에서 메시만 빌려와 거기에 세팅한다. 액터 스폰은 0. 호버 셀이 바뀔 때만 갱신하고, 안 바뀌면 아무것도 안 한다(Tick 0).

가장 중요한 건 **프리뷰 = 배치**가 보장돼야 한다는 거다. 고스트가 보여준 위치·크기·회전과 실제로 클릭했을 때 놓이는 결과가 다르면, 그 프리뷰는 거짓말이다. 그래서 고스트의 메시 fit·중심 산식을 실제 배치에 쓰는 함수(`OJJ_ComputeMeshFitScale`, `GetMachinePlacementLocation`)와 **똑같이** 재사용했다. 1~4편에서 만든 배치 산식을 그대로 빌려온 것이다.

이건 1.3편부터 이어온 "호버 = 프리뷰 = 배치는 같은 판정"이라는 단일 진실원 원칙의 연장이다. 표현이 바닥칸 색에서 고스트 메시로 바뀌었을 뿐, 판정의 출처는 하나로 유지된다.

## 2. Nanite 메시는 고스트가 안 보였다

고스트를 띄우는 방식은 **Overlay Material 패스**다. 원본 메시 텍스처 위에 틴트 머티리얼을 한 겹 덧씌워서, 놓을 수 있으면 초록·없으면 빨강으로 물들인다. 유효/무효는 `bValid` 하나로 `GhostValidMID`(초록)와 `GhostInvalidMID`(빨강) 중 하나를 골라 `SetOverlayMaterial`로 입힌다.

여기서 첫 번째 함정에 빠졌다. **고스트가 아예 안 보였다.**

원인은 Nanite였다. UE5.7 Substrate 환경에서 Nanite 메시는 translucent overlay 패스를 렌더하지 않는다. 그러니 원본 메시는 멀쩡히 보이는데, 그 위에 덧씌운 반투명 틴트만 증발했다. 고스트는 "원본 + 틴트"인데 틴트가 안 그려지니, 결과적으로 고스트가 안 보이는 것처럼 됐다.

해결은 고스트 컴포넌트에 한정해 `SetForceDisableNanite(true)`. 고스트는 호버 한 프레임짜리 미리보기라 Nanite의 이점(대량 폴리곤 최적화)이 필요 없고, 끄면 overlay 패스가 정상적으로 그려진다.

이 함정은 한 번으로 안 끝났다. Foundation 고스트(평판), 사다리 고스트에서도 같은 증상이 재발했다 — Nanite를 쓰는 메시는 전부 같은 우회가 필요했다. "translucent overlay가 안 보이면 Nanite를 의심하라"가 이 프로젝트의 교훈으로 남았다.

회전도 맞춰야 했다. 방향성 머신은 고스트가 90° 어긋나면 "입구가 어디로 가는지"를 거꾸로 보여준다. 그래서 액터 yaw에 메시 상대 회전(+90° 시각 보정)을 합성해서, 고스트의 방향과 실제 배치 방향을 일치시켰다. R키로 회전하면 고스트가 메시 모양째로 90°씩 돈다.

## 3. 반투명끼리 색이 섞였다 — 그리드 시각 위계 (#215)

두 번째 함정은 더 미묘했다. 빨강 오버레이가 깔린 셀 위에 호버를 올렸더니 **주황색**이 됐다.

원인은 반투명 합성이었다. 그리드에는 두 종류의 시각 정보가 있다 — **오버레이**(이 셀이 buildable인가 blocked인가 하는 *정보*)와 **호버**(지금 커서가 가리키는 *액션*). 그런데 둘이 같은 반투명 머티리얼을 공유하니, 빨강 오버레이(blocked) 위에 빨강도 아닌 호버가 겹치면서 색이 섞여 주황이 됐다. 정보와 액션이 시각적으로 엉킨 것이다.

해결은 **MID를 용도별로 분리**하는 거였다. 오버레이는 불투명도 0.1~0.3의 차분한 정보 레이어로, 호버는 불투명도 0.9의 선명한 액션 레이어로 갈랐다. 둘이 다른 MID를 쓰니 색이 섞일 일이 없다.

여기서 한 걸음 더 들어가, **격자선과 채움을 분리**했다.

```cpp
void AOJJ_Grid::OJJ_SetTileParams(UMaterialInstanceDynamic* MID,
                                  const FLinearColor& FillColor, float FillOpacity) const
{
    if (!MID) return;

    // 채움(분류 의미): 연하게 — 정보는 깔리되 튀지 않게
    MID->SetVectorParameterValue(TEXT("BaseColor"), FillColor);
    MID->SetScalarParameterValue(TEXT("Opacity"), FillOpacity);

    // 선(셀 경계 = 스냅 기준선): 항상 선명 — 채움 투명도와 무관
    // 윤곽선 모드면 선 색 = 분류색
    MID->SetVectorParameterValue(TEXT("LineColor"), bOutlineGridStyle ? FillColor : GridLineColor);
    MID->SetScalarParameterValue(TEXT("LineOpacity"), GridLineOpacity);
}
```

왜 분리했나. **격자선은 스냅의 기준선**이다. 플레이어가 "내 머신이 이 칸 경계에 맞춰 놓인다"를 읽는 가장 중요한 선이다. 그런데 채움(분류색)을 진하게 깔면 그 기준선이 묻힌다. 그래서 채움 투명도가 아무리 변해도 선은 항상 선명하게 유지되도록, 한 머티리얼(`M_OJJ_GridFloor`) 안에서 선과 채움을 WorldPosition으로 독립 합성하고 MID로 따로 주입했다. 정보(채움)는 연하게, 기준(선)은 또렷하게.

## 4. 분류 오버레이와 철거 하이라이트

위 위계 위에서 두 가지 시각 레이어가 더 돌아간다.

**지형 분류 오버레이.** 그리드 전체를 셀 종류별로 물들인다 — buildable(청), blocked(적), water(파랑), 그리고 캐릭터가 서 있는 셀(노랑). 14편(지형 분류)·16편(물 분류)에서 격자가 셀을 어떻게 나누는지 정했는데, 이건 그 분류를 *눈에 보이게* 하는 면이다. 참고로 캐릭터 셀(노랑)은 시각 전용이라 그리드 점유 장부에는 등록하지 않는다 — 보여주기만 하고 배치 판정에는 안 낀다.

**철거 하이라이트.** Demolish 서브모드에 들어가 커서를 머신에 올리면, 그 머신이 차지한 **전체 셀**이 빨강으로 칠해진다. 클릭하면 삭제. 여기서 재밌는 건, 이 빨강 하이라이트가 새 코드가 아니라 **배치 호버 ISM을 그대로 재사용**한다는 점이다.

```cpp
void AOJJ_Grid::OJJ_HighlightCellsInvalid(const TArray<FIntPoint>& Cells)
{
    ClearHoverPreview();  // 배치 호버를 먼저 비우고, 철거 대상만 빨강으로

    for (const FIntPoint& Cell : Cells)
    {
        const FVector Loc(CellCenter.X, CellCenter.Y,
                          OJJ_GetCellVisualBaseZ(Cell) + 2.0f + HoverExtraZLift);
        const FVector InstScale(CellSize / 100.0f, CellSize / 100.0f, 1.0f); // 배치 호버와 동일 규칙
        TargetISM->AddInstance(FTransform(FRotator::ZeroRotator, Loc, InstScale));
    }
}
```

배치할 때 쓰던 셀 강조 규칙(스케일·Z 리프트)을 철거에도 그대로 쓴다. "놓을 때 칸을 비추는 법"과 "부술 때 칸을 비추는 법"이 같은 코드라, 시각 언어가 일관된다. (광맥·WaterArea처럼 맵 고정물은 철거 대상에서 제외한다.)

## 5. 하나의 시스템, 여러 가지 모양 — 고스트 다형화

마지막으로, 이 글이 "막간 — 비주얼 총정리"인 이유. 고스트는 머신 하나만 위한 게 아니다. 같은 `GhostMeshComp`/MID 인프라로 그동안 만든 모든 건축물을 미리 보여준다.

| 대상 | 고스트 표현 | 연계 |
|---|---|---|
| 머신 | 메시 fit + 회전 | Phase 1·2 |
| Foundation 평판 | Nanite translucent 박스 | 14편 |
| 램프 | 경사 데크(빗변 스케일 + pitch 재현) | 15편 |
| 펌프 | 수면 Z 안착 | 16편 |
| 사다리 | 박스 인디케이터 | 17편 |

`OJJ_ShowGhostFor{Machine, Foundation, Ramp, Ladder}` — 표현은 다섯 가지지만 바닥의 인프라는 하나다. Foundation 고스트를 만들 때 Nanite 우회를, 펌프 고스트를 만들 때 수면 Z 안착을, 사다리 고스트를 만들 때 박스 인디케이터를 각각 붙였을 뿐, GhostMeshComp와 Valid/Invalid MID는 공유한다.

그래서 14~17편을 쭉 따라온 독자에게 이 글은 일종의 회수다. Foundation도, 램프도, 펌프도, 사다리도 — 각 편에서 "놓는 법"을 다뤘다면, 여기서는 그 전부가 **놓이기 전에 어떻게 보이는가**를 한 시스템으로 묶는다.

## 정리 — 보이지 않으면 못 짓는다

빌드 게임에서 비주얼은 장식이 아니다. 플레이어가 클릭하기 전에 결과를 정확히 보지 못하면, 그 게임은 못 짓는 게임이다. 이 막간에서 고친 것들 — 

- 바닥칸 색칠 → 실제 메시 고스트(모양·방향·높이가 보임)
- Nanite 우회(안 보이던 고스트를 보이게)
- MID 위계 분리(정보와 액션이 색으로 안 엉키게)
- 선/채움 분리(스냅 기준선이 안 묻히게)

— 는 전부 "보여주는 것이 곧 판정"이라는 한 원칙으로 모인다. 고스트가 보여준 그대로 놓이고, 오버레이가 칠한 그대로 판정된다. 표현과 판정이 같은 출처를 공유할 때, 플레이어는 화면을 믿고 지을 수 있다.

다음 편은 경사 컨베이어와 메시 개편으로 돌아간다.
